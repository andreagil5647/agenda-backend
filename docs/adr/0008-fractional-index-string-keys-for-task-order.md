# 0008. Fractional-index string keys for task order

- Status: Accepted
- Date: 2026-10-08

## Context

Tasks are reordered by drag and drop, and a move must change one document, not renumber the
list (see [ADR 0006](0006-optimistic-concurrency-with-version-etags.md) on concurrent edits).
The first implementation stored decimal strings and averaged them, which sorted incorrectly
and lost precision (see debugging note 0003).

## Options considered

- **Integer positions with renumbering**: simple to sort, but every move rewrites many
  documents and conflicts with concurrent tabs.
- **Floating-point midpoints**: one write per move, but precision runs out after ~50 inserts
  into the same gap and needs a rebalancing job.
- **Fractional-index string keys**: one write per move, no precision limit, sorts with a plain
  string comparison in MongoDB.

## Decision

`order` is a base-62 fractional key. `keyBetween(lower, upper)` in `src/domain/task-order`
returns a key strictly between two neighbours (either may be open). The module is pure and
has no framework or database imports.

## Consequences

- A move is a single versioned update; there is no rebalancing step.
- Keys grow by about one character per ~60 repeated insertions in the same gap, which is
  negligible for a personal task list.
- Keys generated by the old scheme (`"1.000000"`) are invalid. The deployed database only
  holds disposable demo data, so no migration is provided.
- `order` is opaque to clients: they send neighbour ids, never keys.
